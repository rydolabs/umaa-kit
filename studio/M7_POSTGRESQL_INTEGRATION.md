# M7: actual PostgreSQL Studio API and leased Worker

This increment leaves SDK, simulator and independent Verifier unchanged; it is **not UMAA conformance**.

## Database and deployment

Use a dedicated PostgreSQL 15+ database. Apply migrations in order:
\`studio/db/migrations/001_initial_postgresql.sql\`, then
\`studio/db/migrations/002_worker_leases.sql\`. Never run \`init-dev\` for production PostgreSQL. Configure the API and independent workers with the same \`STUDIO_DATABASE_URL=postgresql+psycopg://...\` and a private shared \`STUDIO_STORE_DIR\`.

## Lease protocol and limits

Claim is atomic via PostgreSQL \`FOR UPDATE SKIP LOCKED\`; a worker obtains a fresh, unique lease token and expiry. A heartbeat renews the lease. A recovering worker may reclaim expired \`RUNNING\` rows. Completion acquires the row lock and validates token/status/expiry before recording artifacts and verdict; a stale worker cannot overwrite a fresh result. After three expired claims, a job fails closed with an audit record and does not starve the queue. Generated bytes are content addressed; a crashed worker may leave orphaned, unpublished bytes which require future garbage collection.

SQLite remains single-worker **development only**, not equivalent multiworker locking. Worker generation is not an OS sandbox and uploads should not be treated as trusted in a public deployment.
